## 0.0 十分钟看懂本方案（通俗导读；工程契约从 §1 开始）

### 这件事是什么

做一个 Roblox 偶像养成游戏的第一版。玩家选一首歌，跟着节奏按四个键，按得越准分数越高，分数换成粉丝，粉丝数进全服排行榜。

### 游戏跑在哪三个地方

| 地方 | 是什么 | 负责 |
|---|---|---|
| 玩家手机 | 玩家自己的设备 | 玩和看 |
| Roblox 游戏服务器 | Roblox 替我们托管的电脑，所有玩家都连着它 | 算和记 |
| Roblox 云存储 | Roblox 提供的永久保存空间 | 存 |

**不需要自己租云服务器。**

### 谁干什么

| 部分 | 在哪 | 只做什么 | 不做什么 |
|---|---|---|---|
| 界面 | 手机 | 显示菜单、结算页、排行榜，收集点击 | 不算分、不改粉丝 |
| 节奏玩法 | 手机 | 加载并播放歌曲、落音符、判定每一下准不准，出一张成绩单 | 不决定涨多少粉 |
| 舞台 | 手机 | 让角色跳舞、打灯光 | 不影响得分 |
| 歌曲库 | 两边都能读 | 提供歌曲清单和每首歌的参数 | 只读，谁也不改它 |
| 裁判 | 服务器 | 核对成绩单，算涨粉数 | 不碰存档 |
| 档案员 | 服务器 | 唯一能读写玩家存档的人 | 不判断成绩真假 |
| 榜单员 | 服务器 | 只管排行榜 | 不管别的存档内容 |

### 数据怎么流

```
【玩家手机】               【Roblox 游戏服务器】        【Roblox 云存储】

 界面：选歌
  ▼
 节奏玩法：先把歌加载好
  │ ① 加载成功后才申请开局
  └─────────────────────► 裁判：开一张"开局单"
                            (谁、哪首歌、几点开始)
  ┌──────── ② 允许开始 ◄────┘
  ▼
 节奏玩法 ─(每次按键)─► 舞台
  │  倒数 3 秒后放歌
  │  本地判定，全程不联网
  │
  │ ③ 歌结束，交成绩单
  └─────────────────────► 裁判：核对成绩单
                            │ 不合理 → 作废，不涨粉
                            │ 合理 → 算出涨粉数
                            ▼
                          档案员：改内存里的存档
                            │
  ┌─ ④ 得分、涨粉、新粉丝数 ◄─┤
  ▼                         │ (立即排队保存；另有
 界面：显示结算页             │  每 2 分钟 + 离开时)
                            ▼
                          档案员：写入云端 ────────► 玩家存档
                            │ 保存成功后才通知
                            ▼
                          榜单员：同步粉丝数 ──────► 排行榜
```

三个要点：

- 打歌过程中手机不联网，因为每次按键都问服务器会有延迟，手感会很差。只在开头和结尾各联系一次。
- 歌要先加载好再申请开局，否则加载慢的玩家会被裁判误判成「用时不对」。
- 排行榜只收**已经存进云端**的粉丝数。这样排行榜上永远不会出现玩家存档里没有的粉丝。

### 一个例子走完

1. 玩家 8801 选了 `neon_night`（91 秒，180 个音符）。手机把歌加载好，然后申请开局。裁判记下开局单：8801、`neon_night`、20:00:00。
2. 手机倒数 3 秒后放歌。玩家按出 140 个完美（各 100 分）、30 个不错（各 50 分）、漏 10 个，共 15500 分。
3. 20:01:35 手机交成绩单。裁判核对：编号对得上这张开局单、三项次数加起来正好 180、用时 95 秒在 92–124 秒的合理范围内。通过。
4. 裁判算涨粉：15500 ÷ 满分 18000 ≈ 86%，乘以这首歌的基础粉丝 100，涨 86 粉。
5. 档案员把内存里的粉丝数从 1200 改成 1286，局数从 14 改成 15，这首歌的最高分从 14200 改成 15500。界面马上显示：15500 分、+86 粉丝、现有 1286 粉丝。
6. 档案员把存档写进云端。写成功后，榜单员才把 1286 报给排行榜。

### 必须提前知道的四件事

**一、目标玩家（16 岁以下）不是上线就能触达的。**
- 是什么：Roblox 从 2026 年 5 月起把发布分成三档。发布给 16 岁以上只需要完成年龄验证；要让 16 岁以下的玩家看到，除了证件验证、两步验证、发布费或订阅，还要通过一轮评估：60 天内有一定数量的「高度活跃且已验证年龄的 16 岁以上玩家」玩过。这个数量在 2026-11-19 的官方文档里是 250，此前从 500 降下来，之后可能继续降。
- 为什么要管：偶像养成的核心受众正是 16 岁以下。游戏必须先靠 16 岁以上的玩家攒够人数，才能进入真正的目标市场。
- 不管会怎样：做完上线后发现目标玩家根本搜不到这个游戏。细则见 §4.3。

**二、第一版的排行榜防不住作弊。**
- 是什么：成绩是在玩家手机上算的。会改数据的人只要申请开局、等够一首歌的时间、再提交「全部完美」，就能通过裁判的全部核对，一个键都不用按。
- 为什么要管：粉丝数直接决定排行榜。
- 不管会怎样：榜首可能是挂机刷出来的。好在有一个上限：一首歌的时间内最多涨这首歌的基础粉丝数，所以作弊者的涨粉速度不会超过「每首都打满分的真人」，区别只是他能 24 小时挂着刷。M1 接受这个风险，见 §4.4。

**三、存档有跨服务器保护，代价是偶尔要等。**
- 是什么：玩家离开一台服务器后马上进另一台时，前一台可能还没存完。如果后一台直接读，会读到旧进度，之后再把旧进度存回去，新进度就没了。所以每份存档同一时间只允许一台服务器持有，后来的服务器要等前一台交还。
- 为什么要管：这种情况单设备正常重进就会发生，不需要多设备。
- 代价：重进时最多等约 30 秒。如果前一台服务器是崩溃的，要等 6 分钟才能进。

**四、存档通常几秒内就写进云端，但不是绝对的。**
- 是什么：每局结算后立即排队保存。Roblox 的存储服务偶尔会出故障，保存会失败并重试。
- 后果：服务器正好在保存前崩溃，或存储故障持续较久时，会丢失这段时间的进度。连续保存失败时界面会提示玩家。

## 1. 数据模型

> 命名约定：模块名与文件名用 `PascalCase`，数据字段用 `camelCase`，常量用 `UPPER_SNAKE_CASE`，名字要能单独看懂。

### 1.1 歌曲库条目（只读配置，`src/shared/SongCatalog.luau`）

| 字段 | 类型 | 示例 | 说明 |
|---|---|---|---|
| `songId` | string | `"neon_night"` | 歌曲唯一标识，永不改名 |
| `songDisplayTitle` | string | `"Neon Night"` | 显示给玩家的歌名 |
| `songAudioAssetId` | string | 待选曲后填 | Roblox 音频素材编号 |
| `songBeatsPerMinute` | number | `120` | 每分钟拍数 |
| `firstBeatOffsetSeconds` | number | `0.5` | 音频里第一拍出现的时间。每首歌人工听出来填 |
| `songDurationSeconds` | number | `91` | 音频文件的实际长度（秒） |
| `baseFanReward` | number | `100` | 满分时涨的粉丝数 |

🔴 音符总数和满分**不存进歌曲库**，一律由 `NoteChartGenerator` 生成的音符列表得出，避免两处数字不一致。

🔴 手机加载完音频后，要比对音频的实际长度与 `songDurationSeconds`，相差超过 0.5 秒视为歌曲配置错误，拒绝开局。

### 1.2 谱面（由 `NoteChartGenerator` 生成，不保存）

每个音符：

| 字段 | 类型 | 说明 |
|---|---|---|
| `noteIndex` | number | 从 0 开始的序号 |
| `noteHitTimeMilliseconds` | number | 应该按下的时刻，以音频播放位置计，整数毫秒 |
| `noteLaneIndex` | number | 轨道，0–3 |

M1 生成规则：

- 第 k 个音符（k = 0, 1, 2 …）的 `noteHitTimeMilliseconds = round(firstBeatOffsetSeconds × 1000 + k × 60000 ÷ songBeatsPerMinute)`
- 只生成 `noteHitTimeMilliseconds ≤ (songDurationSeconds − CHART_TAIL_MARGIN_SECONDS) × 1000` 的音符，`CHART_TAIL_MARGIN_SECONDS = 1`。这保证最后一个音符的判定在歌曲结束前完成
- `noteLaneIndex` 由以 `songId` 为种子的伪随机数决定
- 🔴 同一首歌在手机和服务器上生成的列表必须完全相同
- 🔴 `songNoteCount` = 生成出的列表长度，不用公式另算；`songMaxScore = songNoteCount × 100`

`neon_night` 的结果：音符在 500、1000、1500 … 90000 毫秒，共 180 个，满分 18000。

### 1.3 判定与计分（`src/shared/SongScoreCalculator.luau`）

以「按下时的音频播放位置」与 `noteHitTimeMilliseconds` 的差来判定：

| 判定 | 时间误差 | 单个得分 |
|---|---|---|
| 完美 perfect | ≤ 50 毫秒 | 100 |
| 不错 great | ≤ 120 毫秒 | 50 |
| 漏掉 missed | 播放位置超过该音符时刻 120 毫秒仍未按 | 0 |

以上是初始值，试玩后调整。调整只改这一个文件。

- `songScore = perfectHitCount × 100 + greatHitCount × 50`
- `fanCountGained = floor(baseFanReward × songScore ÷ songMaxScore)`

### 1.4 开局单与上一局结果（只在服务器内存里，不保存）

每个玩家在服务器内存里有两样东西：

**当前开局单**（没有在打的局时为空）：

| 字段 | 类型 | 示例 |
|---|---|---|
| `songPlaySessionId` | string | 服务器生成的随机唯一编号 |
| `playerUserId` | number | `8801` |
| `songId` | string | `"neon_night"` |
| `serverStartedAtUnixSeconds` | number | 服务器记下的开局时间 |

**上一局的结算结果**：`songPlaySessionId` 加上当时返回给手机的整份应答（通过或拒绝都记）。用于识别重复提交。

规则：

- 🔴 每个玩家同一时间只有一张当前开局单。再次开局会顶掉旧的
- 🔴 只有编号与当前开局单一致的成绩单或取消请求才能动它。编号对不上的请求一律只拒绝、不改任何状态

### 1.5 成绩单（手机 → 服务器）

| 字段 | 类型 | 示例 |
|---|---|---|
| `songPlaySessionId` | string | 开局时拿到的编号 |
| `perfectHitCount` | number | `140` |
| `greatHitCount` | number | `30` |
| `missedNoteCount` | number | `10` |

🔴 成绩单里**没有分数字段**。分数由服务器用三项次数重新算，手机报的分数一律不采信。

### 1.6 玩家存档

- 存储：标准数据存储 `PlayerSaveData_v1`，键 `player_<playerUserId>`

| 字段 | 类型 | 结算前 | 结算后 |
|---|---|---|---|
| `saveDataSchemaVersion` | number | `1` | `1` |
| `fanCount` | number | `1200` | `1286` |
| `totalSongsPlayedCount` | number | `14` | `15` |
| `bestScoreBySongId` | 表 | `{ neon_night = 14200 }` | `{ neon_night = 15500 }` |
| `firstJoinedAtUnixSeconds` | number | 不变 | 不变 |
| `lastSavedAtUnixSeconds` | number | 上次保存时间 | 本次保存时间 |
| `gameServerSessionLock` | 表或空 | 见 §3.4 | 见 §3.4 |

新玩家的初始存档：`fanCount = 0`、`totalSongsPlayedCount = 0`、`bestScoreBySongId = {}`。

**迁移**：以后改存档结构时，`saveDataSchemaVersion` 加 1，由 `PlayerSaveDataKeeper` 在读取时把旧版本升级成新版本。M1 只有版本 1，无迁移。

### 1.7 粉丝排行榜

- 存储：有序数据存储 `FanCountLeaderboard_v1`，键 `tostring(playerUserId)`，值 `fanCount`
- 🔴 写进排行榜的只能是**已经成功保存到 `PlayerSaveData_v1` 的** `fanCount`。因此排行榜上的数字永远不会高于玩家存档
- 每台服务器每 60 秒读一次前 100 名并缓存，手机只读这份缓存
- 同步规则见 §3.5

⚠️ 有序数据存储不能直接查「某人排第几」。M1 只给前 100 名显示名次，其余显示「100 名以外」。

## 2. 接口契约（手机 ↔ 服务器）

所有通道放在 `ReplicatedStorage.Remotes`，名字集中定义在 `src/shared/RemoteNames.luau`。

### 2.1 手机端的开局流程

| 步骤 | 手机做什么 | 失败时 |
|---|---|---|
| 1 | 加载这首歌的音频，等到加载完成。最多等 `SONG_AUDIO_LOAD_TIMEOUT_SECONDS = 20` 秒 | 提示「歌曲加载失败」，回到选歌。**不联系服务器** |
| 2 | 比对音频实际长度与 `songDurationSeconds`（§1.1） | 同上 |
| 3 | 调用 `RequestStartSongPlaySession` | 按 `rejectionReason` 提示，回到选歌 |
| 4 | 倒数 `SONG_START_COUNTDOWN_SECONDS = 3` 秒，然后播放 | — |
| 5 | 播放中出现下表任一情况 → 取消本局 | 见下 |
| 6 | 音频正常播放到结尾 → 调用 `SubmitSongPerformanceScoreCard` | 调用出错时用同一张成绩单最多重试 2 次 |

取消本局的情况（停止播放，发送 `CancelSongPlaySession`，回到选歌，不涨粉）：

| 情况 | 判据 |
|---|---|
| 玩家主动退出 | 点了退出按钮 |
| 播放停滞 | 音频播放位置连续 1 秒没有前进（切到后台、设备卡死等都会表现为这个） |
| 歌曲提前结束 | 最后一个音符的判定时刻之前，音频就报告播放结束 |

### 2.2 `RequestStartSongPlaySession`（手机请求，服务器应答）

| 方向 | 内容 |
|---|---|
| 请求 | `songId` |
| 应答（成功） | `{ isAccepted = true, songPlaySessionId }` |
| 应答（失败） | `{ isAccepted = false, rejectionReason }` |

失败原因：`UnknownSong`（歌曲库里没有这首歌）、`SaveDataNotLoaded`（存档还没读完）。

### 2.3 `SubmitSongPerformanceScoreCard`（手机请求，服务器应答）

| 方向 | 内容 |
|---|---|
| 请求 | §1.5 的成绩单 |
| 应答（通过） | `{ isAccepted = true, isDuplicateSubmission, songScore, fanCountGained, newFanCount, isNewBestScore }` |
| 应答（拒绝） | `{ isAccepted = false, isDuplicateSubmission, rejectionReason }` |

裁判**严格按下面的顺序**处理：

| # | 条件 | 处理 | 是否改动状态 |
|---|---|---|---|
| 1 | 成绩单编号等于「上一局的结算结果」里的编号 | 原样返回当时的应答，`isDuplicateSubmission = true` | 不改。🔴 不重复涨粉 |
| 2 | 玩家没有当前开局单 | 拒绝，`NoActiveSongPlaySession` | 不改 |
| 3 | 成绩单编号与当前开局单不一致 | 拒绝，`SongPlaySessionMismatch` | 不改。🔴 当前这一局不受影响 |
| 4 | 编号一致 | 当前开局单作废，继续往下核对 | 开局单清空 |
| 5 | 三项次数不全是非负整数，或相加不等于 `songNoteCount` | 拒绝，`HitCountsInvalid` | 把这次拒绝记为上一局结果 |
| 6 | 用时不在范围内（见下） | 拒绝，`ElapsedTimeOutOfRange` | 把这次拒绝记为上一局结果 |
| 7 | 全部通过 | 算分、算涨粉、交给档案员改内存存档并排队保存 | 把这次通过记为上一局结果 |

用时 = 服务器当前时间 − `serverStartedAtUnixSeconds`，合理范围：

- 下限：`SONG_START_COUNTDOWN_SECONDS + songDurationSeconds − 2`
- 上限：`SONG_START_COUNTDOWN_SECONDS + songDurationSeconds + 30`

`neon_night` 的范围是 92–124 秒。

`newFanCount` 是内存里的最新值，此刻不一定已写进云端。

### 2.4 `CancelSongPlaySession`（手机通知服务器，不需要应答）

内容：`songPlaySessionId`。编号与当前开局单一致时，开局单作废；不一致时忽略。不涨粉，不记为上一局结果。

### 2.5 `RequestFanCountLeaderboardTopEntries`（手机请求，服务器应答）

应答：`{ leaderboardEntries, refreshedAtUnixSeconds }`，其中每条为 `{ leaderboardRank, playerUserId, playerDisplayName, fanCount }`，最多 100 条。

### 2.6 `PlayerSaveDataSnapshotChanged`（服务器主动通知手机）

内容：`{ fanCount, totalSongsPlayedCount, bestScoreBySongId, isSaveDataPersistenceDelayed }`。玩家进入游戏读完存档时发一次，之后每次内存存档变化或保存状态变化时发一次。界面只根据它刷新显示。

`isSaveDataPersistenceDelayed` 为真表示保存连续失败（§3.4），界面显示「进度暂时无法保存」。

### 3.3 各部分的硬约束

- 🔴 **裁判**不直接读写数据存储，只调用档案员
- 🔴 `RobloxPlayerSaveDataStorage` 是唯一接触 `PlayerSaveData_v1` 的文件；`RobloxFanCountLeaderboardStorage` 是唯一接触 `FanCountLeaderboard_v1` 的文件

- 🔴 **节奏玩法**以音频的实际播放位置为时钟，不用「从开始到现在过了多久」推算

### 3.4 存档：跨服务器保护与保存规则

#### 持有锁

`gameServerSessionLock` 存在玩家存档里，表示这份存档当前归哪台服务器：

| 字段 | 说明 |
|---|---|
| `sessionLockId` | 服务器在读取这位玩家存档时生成的随机唯一编号 |
| `lockRefreshedAtUnixSeconds` | 最近一次成功保存的时间 |

常量：`SESSION_LOCK_EXPIRY_SECONDS = 360`。锁超过这个时间没刷新即视为过期（原服务器已崩溃）。

🔴 所有对玩家存档的读和写都必须是「读出当前值 → 判断 → 写回」一步完成的原子操作，不允许先读后写分两步。

#### 读取（玩家进入时）

| 云端存档的状态 | 处理 |
|---|---|
| 没有锁，或锁已过期 | 写上自己的锁，取得存档 |
| 有别的服务器的未过期锁 | 放弃，每 5 秒重试一次，最多 6 次 |
| 存储服务报错 | 同上重试 |
| 重试用尽 | 把玩家请出游戏，提示「存档正在保存，请稍后重新进入」 |

🔴 读取成功之前拒绝开局（`SaveDataNotLoaded`）。🔴 任何失败情况都不得用初始存档顶替。

#### 写入

每次写入时先核对云端的 `sessionLockId` 是否仍是自己的：

| 云端的锁 | 处理 |
|---|---|
| 是自己的 | 写入存档，并把 `lockRefreshedAtUnixSeconds` 更新为当前时间 |
| 不是自己的（已被别的服务器接管） | 🔴 放弃写入，停止这位玩家此后的一切保存，把玩家请出游戏。内存里没存上的进度作废并记日志 |

最后一次保存（玩家离开、服务器关闭）在同一次写入里清空 `gameServerSessionLock`。

#### 何时保存

| 时机 | 说明 |
|---|---|
| 每局结算通过后 | 立即排队 |
| 每 120 秒 | 即使没有改动也写，用于刷新锁 |
| 玩家离开 | 最后一次保存，交还锁 |
| 服务器关闭 | 对所有在线玩家并行做最后一次保存。Roblox 只给 30 秒 |

#### 保存的并发与失败

- 🔴 同一玩家同一时间最多有一次保存在进行。进行中又来了新的保存请求，只记下「这次完成后再存一次」，不并行
- 🔴 用改动序号判断是否还有没存的内容：内存存档每改一次，`inMemoryChangeRevision` 加 1；保存开始时记下当时的序号；保存成功后把 `lastSavedChangeRevision` 设为**开始时记下的**那个序号，而不是当前序号。只要 `inMemoryChangeRevision > lastSavedChangeRevision` 就还要再存。这样保存进行期间产生的新成绩不会被漏掉
- 保存失败：保持未保存状态，按 2 秒、4 秒、8 秒的间隔重试，一轮最多 3 次。仍失败则等下一个时机再来
- 一轮重试全部失败后，`isSaveDataPersistenceDelayed` 置为真并通知手机；任何一次保存成功后恢复为假
- 最后一次保存最多重试 5 次。全部失败则放弃并记日志，锁靠过期自动释放

### 3.5 排行榜同步

榜单员为每位在线玩家在内存里记 `lastLeaderboardSyncedFanCount`。

| 时机 | 动作 |
|---|---|
| 玩家存档读取成功后 | 用存档里的 `fanCount` 同步一次。这一步补上「上次服务器在存档成功后、同步排行榜前崩溃」造成的缺口 |
| 每次存档保存成功后 | 若刚保存的 `fanCount` 不等于 `lastLeaderboardSyncedFanCount`，同步 |
| 同步失败 | 不重试、不报错给玩家，等下一次保存成功后再比对 |

- 🔴 排行榜的任何故障都不得阻断结算和存档
- 🔴 榜单员只从「保存成功」这个事件里拿 `fanCount`，不读内存里的最新值

正常情况下，一局打完到出现在别人看到的榜单上：保存几秒，加上最长 60 秒的缓存刷新。

### 3.6 数据存储限额（来自官方文档，见 §7）

每台服务器每分钟的默认限额：标准读、标准写各 `60 + 玩家数 × 40` 次；有序写 `30 + 玩家数 × 5` 次；有序列表读 `5 + 玩家数 × 2` 次。整个游戏另有按在线人数计算的总限额：标准写每分钟 `300 + 在线人数 × 20` 次。存档的原子读写同时占用一次读额度和一次写额度。

按本设计估算，一台 20 人的服务器每分钟：定时保存 10 次，结算保存最多约 13 次（以 91 秒的歌为例，两次结算至少相隔 92 秒），合计约 23 次存档读写，限额 860；有序写最多约 13 次，限额 130；有序列表读 1 次，限额 45。平均每位玩家每分钟约 1.2 次写，游戏总限额是每人 20 次。

### 3.7 舞台与动画

- M1 只用 Roblox 官方提供的舞蹈动画，循环播放
- 自制动画留到 M1 之后：Studio 的「Live Animation Creator」测试功能可把单人、单镜头、15 秒以内的视频转成动画，所以每段自制舞蹈不超过 15 秒

### 5.1 测试环境

### 5.2 测试清单

- 多人压力测试：M1 没有玩家量
- 作弊攻防：M1 明确不防（§4.4）

## 9. v1.1 修订对照

审计来源：用户转交的一份针对 v1.0 的设计契约审计（2026-11-19）。

| 审计项 | 核实结论 | 处置 | 落在哪 |
|---|---|---|---|
| P1 存档覆盖不只发生于双设备 | 属实。官方文档明确描述了离开 A 立即进 B 的场景 | 采纳：会话锁进 M1 | §3.4、§1.6 |
| P1 排行榜先于存档落盘 | 属实。v1.0 的流程里崩溃后榜单会留下存档里没有的粉丝数 | 采纳：只同步已保存的粉丝数，读取时补同步 | §1.7、§3.5、验收门 F |
| P2 旧成绩单会作废新局 | 属实。v1.0「无论通过与否即作废」与编号核对组合后会出错 | 采纳：编号不符只拒绝；重复提交原样返回 | §1.4、§2.3、验收门 E |
| P2 保存的失败与并发未定义 | 属实 | 采纳：串行、改动序号、重试、失败提示 | §3.4 |
| P2 只有拍速无法定第一拍 | 属实 | 采纳：加 `firstBeatOffsetSeconds`，定义音符时刻与末尾留白，数量取列表长度 | §1.1、§1.2 |
| P2 开局计时含加载时间 | 属实 | 采纳：加载成功后才申请开局；定义取消规则；用时范围改为含倒数 | §2.1、§2.3、§2.4 |
| 作弊风险表述不准 | 属实。等够时间提交全完美即可通过 | 采纳：改写风险描述，补上限说明和「不得按名次发奖」 | §0.0、§4.4、拍板 14 |
| 测试环境需隔离 | 属实。官方文档证实 Studio 访问真实存储 | 采纳：两个游戏；补四类测试 | §5 |
| 发布规则保留不确定性 | 部分属实。加急费与退款条件属实；「降到 100」只在搜索摘要里见到，「11 月」未能核实 | 采纳：门槛写成会变的数字，100 标为未核实；加急费表述改准 | §4.3、§7 |
