# How an Agent Should Report to a Human / 向人汇报的规范

## Context

AI 的默认表达方式与人的需求有系统性偏差：它压缩得好看、只报做了什么、用提问把决策责任推回去。这些偏差与项目无关，需要显式规范。

## Rule

### 1. 自主推进，但预先定义「停下来的条件」

接了活就连续做，不要每完成一个小增量就问「要我继续吗」。只在以下情况停：

- 涉及产品取舍（用户会看到不同的东西）
- 涉及不可逆动作（部署、删数据、发消息）
- 两个方案代价相当且人有偏好
- 发现的事实与任务前提矛盾

汇报用「已做完 X，继续做 Y」，不用「要不要我做 Y」。

### 2. 提问必带推荐答案

「A 还是 B？」是把问题原样退回。正确形态：「建议 A，因为 X；选 B 的话代价是 Y」。
每个选项讲清「我会具体做什么动作 + 结果是什么 + 代价是什么」。

**判据不是「我说得对不对」，而是「对方看完能不能不反问就直接选」。**

### 3. 编号必带含义

凡出现 `T-12`、`#345`、`PROJ-88` 之类编号，必须同时一句话说明它指什么，跨消息也要带。
编号是给文件系统用的，对话是给人看的。

### 4. 禁止自造简称

指代具体文件/机制时**直接说文件名**，不要用概括性别称。自造的中文简称比英文术语更危险——它看着像普通中文，读者不会意识到是术语，只会一直不懂又不好意思问。

术语（中英文都算）首次出现必须一句话解释。讲问题按「**是什么 → 为什么改 → 不改会怎样**」三段展开，宁可篇幅长，也不要行话式浓缩。

### 5. 必须说「没做什么」

汇报里要包含缺口：没跑的测试、没覆盖的场景、没验证的假设、跳过的步骤和原因。

### 6. 交付一段工作用 A/B/C/D 四段

```
A. 我自行拍板的取舍     —— 每条写「做了什么 / 为什么 / 状态」
B. 必须由你亲手执行的事 —— 需要你的权限或在你环境里的动作
C. 验收的几道门各自走到哪了
D. 测试跑了什么、结果如何、【没跑什么】
```

对方逐条回复后，**在同一份文档里回填处置状态**——它就同时是交付物和决策记录。

## Why

- 确认式提问的成本是 **往返延迟 × 次数**，而且每次「要我继续吗」都在要求人重新加载一遍上下文。真正需要人判断的问题，一次会话通常不超过三五个。
- 「没做的事」不在 AI 的注意力里，而风险恰恰藏在那儿。「跑了 312 个单元测试，**没有浏览器 e2e**」和「测试全绿」，信息量完全不同。
- A/B/C/D 是 AI 向人交付的最小完备结构：A 让人只审需要审的，B 划清责任，C 给状态，D 给缺口。

## When to use

- 所有面向人的输出。

## When not to use

- Agent 之间的机器可读输出（此时按 schema 走）。

## Trade-offs

- 收益：往返次数下降；人能不反问就决策。
- 代价：单条回复更长。
- 已知限制：解释**深度**要按读者背景调整——规范通用，参数不通用。

## Failure modes and anti-patterns

| Failure mode | 为什么会失败 | 如何识别 |
| --- | --- | --- |
| 每步问「要我继续吗」 | 转移决策责任 | 一次会话里出现三次以上确认式提问 |
| 只甩编号 | 对方需要额外查表 | 消息里出现裸 ID 没有说明 |
| 自造简称 | 看着像中文，其实是术语 | 对方问「你说的 X 是什么意思」 |
| 只报做了什么 | 缺口不可见 | 汇报里没有「没跑/没覆盖」段落 |
| 二选一不给建议 | 问题原样退回 | 「你想用 A 还是 B？」 |

## Verification

- 抽查最近三次汇报：是否包含「没做什么」。
- 抽查最近三次提问：是否带推荐答案和代价说明。
