# hao-deploy-verification-checklist

为一次生产部署生成两份产物：**部署前风险评估** + **部署后手工核验 checklist**。
所有命令由用户手工在生产执行并回贴结果，你只负责生成和判读。

## 铁律（不可违反）

- **绝不登录生产服务器、绝不主动执行任何生产命令。** 即使你有 ssh 能力、即使命令是只读的。你产出清单，用户执行，用户回贴结果。
- **命令必须基于项目真实代码、命令、表和字段。** 每条命令写出来之前，先去代码里核实：artisan 命令名、表名、字段名、配置键、路由 path 都要 grep 到出处，不允许凭记忆猜测。
- **只读优先。** 优先只读 `php artisan` 命令，其次只读 raw SQL（SELECT/SHOW/EXPLAIN）。任何有副作用的命令（哪怕是"安全的"写入）单独标注 ⚠️ 并说明后果，默认不进清单。

## 输入

- 用户通常会给：仓库 + commit 范围（如"从 5fb86181 到最新 origin/master"）或"部署五仓"。
- 没给范围时：列出各相关仓库的最近 commit（`git -C <repo> log --oneline -10`），向用户确认基线，**不要瞎猜基线**。
- 多仓库部署时，逐仓库分析（先用 `git -C <repo> log --oneline -10` 列出本次涉及的仓库，向用户确认，不要假设仓库清单）。

## 第一步：分析改动面

结合 commit 历史和最终 diff（`git log` + `git diff <base>..<head>`，需要时读具体文件），识别**实际生效**的变化，按维度归类：

1. 业务逻辑（行为变化、算法修正、文案）
2. 数据库（migration、新表/新字段、索引、是否 destructive）
3. 配置与 env（新增/改名/删除的 config 键和 env 变量）
4. 路由与 API（新增/变更/删除的端点，签名/中间件变化）
5. 队列与 job（新 job、queue 名变化、优先级、supervisor 配置是否需改）
6. 定时任务（Kernel.php scheduled task 增删改）
7. 依赖与部署动作（composer/npm 依赖、需要的 reload/dump-autoload 步骤）
8. 功能开关/gate（新 gate 的默认值、部署后处于开还是关）

注意"实际生效"：被 gate 关着的代码、尚未部署的仓库、纯测试/文档改动，要识别出来并降低其核验优先级。

## 第二步：部署前风险评估

回答三个问题，每个都给出依据（引用具体 commit/文件）：

1. **是否对现有数据 destructive？** migration 是否只增不改删；有无 UPDATE/DELETE 类回填；回滚是否安全。
2. **有无部署顺序依赖？** 常见形态：schema 变更集中在某一个仓库，其他仓库不跑 migration——读新 schema 的代码必须等 schema 先部署。先核实本项目的实际纪律（谁负责 migration、谁只 pull），再明确给出部署顺序。
3. **生产 env/config 是否就绪？** 列出本次新引入或必须变更的 env 键清单，让用户逐项核对生产 `.env`。历史教训：legacy 兼容代码在 env 缺失时默认空串，会**静默产出坏数据**而不报错，所以 env 核对必须在部署前完成，不能靠部署后发现。

## 第三步：部署后手工核验 checklist

**按风险和执行顺序排列**（先验致命面：进程/路由/资金；再验功能面；最后验旁路面：日志/统计）。

每项使用固定结构：

```
### N. <检查项标题>（风险：高/中/低）
- 关联改动：<commit/文件，一句话说明验的是什么>
- 执行命令：<只读命令，可直接复制执行>
- 预期结果：<具体的值/行数/状态，不要写"正常即可">
- 异常表现及排查方向：<看到什么算坏、坏了先查哪里>
```

命令编写要点：

- 内网直接 curl backend 时必须带 Host 头（`-H 'Host: <内网服务名>'`），否则反向代理会 403——这类内网直连约定属于项目专属知识，安装后按实际情况改写。
- 切换/迁移类改动，冒烟必须真机打 HTTP 端点（走完整 ALB/nginx/签名链路），不能只跑进程内测试。
- SQL 示例要写全库名/表名，方便直接粘贴。

## 第四步：覆盖关系 + 盲区

清单末尾必须附：

1. **覆盖矩阵**：commit/改动 → 对应检查项编号，确保每个生效改动至少被一项覆盖；纯文档/测试改动标记"无需验证"。
2. **无法直接验证的风险点**：哪些改动只能靠时间观察（如次日凌晨的 cron）、靠真实用户行为触发，给出"何时回来看什么"的观察计划。

## 第五步：判读回贴结果

用户执行后会把输出贴回来。逐项判读：

- 与预期一致 → ✅ 明确说"第 N 项通过"。
- 不一致 → ❌ 先判断是真异常还是预期写错了（不要急着让用户改生产），给出排查方向和下一条只读命令。
- 全部通过后，主动提醒剩余的"时间观察类"风险点及回看时间。

部署完全收官后，如需同步任务板，提示用户可跑 `/hao-task-deployed`（不要替用户跑）。
