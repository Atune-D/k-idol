# hao-explain-to-doc

把一个系统机制的解释**写入文档**，对话里只回 path。解释内容的写法与 `hao-explain-only` 完全一致——**先读 `~/.claude/skills/hao-explain-only/SKILL.md` 的「解释内容规范」一节并严格遵循**（含"先核实、不许编"的前置要求）。那份规范是唯一母本，本 skill 不复制它，避免两处漂移。

与 `dev-log` 的分工：dev-log 记**发生过的事**（事故、决策、里程碑），本 skill 写**系统怎么工作**（机制、数据流、表关系）。

## 第一步：决定文档位置（先分析，再动笔）

1. **搜现有文档。** 在解释对象所属仓库的 docs 体系里搜关键词（表名、命令名、任务号），常见位置：
   - `<项目根>/docs/specs/`（机制/设计定稿——本 skill 最常见的归宿）
   - `<项目根>/docs/plans/`（开发计划，含机制说明的章节）
   - `<项目根>/docs/infra/`（基础设施全景）
   - 各代码仓库自己的 `docs/`
2. **判断合并 vs 新建：**
   - 已有文档在讲同一机制/同一任务域 → **合并**进去（在合适的 section 下新增或扩写），避免同一机制散落两份、日后互相漂移。
   - 找不到贴切的宿主，或解释对象是独立机制 → **新建**。新建文件命名前必须读 `~/.claude/practices/foundations/code-file-naming-rules.md`。
   - 拿不准两个候选位置哪个对 → 问用户，附一句各自的理由，别赌。
3. 这一步的分析在内部完成，**不要**在对话里长篇展示候选比较。

## 第二步：撰写并写入

- 按 hao-explain-only 的「解释内容规范」写完整解释（一句话定位 / ASCII 流程图 / 示例数据表 / 具体例子走流程 / 边界与误解）。
- 合并进现有文档时，融入宿主的结构与风格：标题层级接上、术语与宿主一致、不破坏原有目录；宿主有目录/index 就同步更新。
- 目标文档体系若有登记要求（如 docs-site 的 governance 清单），一并登记。
- 如果新解释**推翻或更新了**其他文档里的旧描述，顺手改一致，或在回复里提醒用户哪份文档已过时。
- **默认不 commit。** 用户明确要求才提交（提交时遵守多仓库纪律：`git -C <repo>`，不裸 `add -A`）。

## 第三步：对话里只返回 path

最终回复格式（保持极简，**绝不在对话里复述解释内容**）：

```
已写入：<项目根>/docs/specs/merchant-data-purge-flow.md
（并入现有文档，新增「数据清空三命令的分工」一节）
```

或新建时：

```
已新建：<项目根>/docs/specs/order-payment-ledger-outbox-explained.md
```

path 之外最多附一行"新建还是并入、并入了哪个 section"。用户想看内容自己会打开文件。
