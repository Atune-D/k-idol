# 从一个真实项目提炼：与 AI 协作中可跨项目通用的方法

> 上游文档：《Claude Code 协作实录》（原始记录，未随本套件分发）
> 本文做的事：把那份记录里的东西过一遍筛子，判断哪些能带走、哪些不能，并给出**为什么**。

---

## 一、先立判据：什么叫"可跨项目通用"

一条实践能不能带走，取决于它**回应的是什么**：

- 回应的是 **AI 协作本身的结构性约束**（会话失忆、上下文有限、模型会编、责任不可委托……）→ **通用**。因为这些约束不随语言、框架、业务域改变。
- 回应的是 **某个技术栈或业务域的特性**（某语言版本的浮点舍入行为、某第三方平台的授权流程、某云厂商的账单）→ **不通用**，只能当案例看。

一个可以随手用的反问：

> **把项目换成"一个人用 Rust 写游戏服务器"，这条还成立吗？**
> 成立 → 通用。不成立 → 是那个项目的专属知识，不是方法。

按这个筛子过一遍，原项目那套东西里**大约七成是通用的**——这个比例本身值得注意：说明这套体系的主体不是"某类项目怎么管"，而是"人和 AI 怎么协作"。

---

## 二、七个结构性约束，和它们各自逼出来的通用做法

这是本文的主体。每条按：**约束是什么 → 原项目怎么做 → 通用形态 → 为什么必然通用 → 换项目时要改什么**。

---

### 约束一：会话没有记忆，每次都从零开始

**原项目的做法**：把判断力外化成四层文件——`CLAUDE.md`（6 条铁律）、`memory/`（85 条项目记忆）、`practices/`（跨项目知识库）、`docs/tasks/`（任务板）。

**通用形态**：任何和 AI 长期协作的项目，都需要一个**外部持久层**。而且这一层要**分层**，分层依据是两个维度：

| 层 | 变化频率 | 作用域 | 内容性质 | 原项目的实例 |
|---|---|---|---|---|
| 铁律 | 几乎不变 | 全局 | **约束**（不许做什么） | `~/.claude/CLAUDE.md`，6 条 |
| 记忆 | 被纠正时增量写 | 单项目 | **事故与偏好** | `memory/`，85 个单文件 + 索引 |
| 知识库 | 定期 triage | 跨项目 | **经验实践** | `practices/`，带 status 字段 |
| 任务板 | 每天 | 单项目 | **状态** | `docs/tasks/active.md` |

**为什么必然通用**：session 边界是 LLM 的架构事实，与项目无关。人靠脑子累积经验，AI 只能靠读文件。不建这一层，你就会**每周把同一件事解释一遍**——而且是无声的损耗，你甚至不会意识到自己在重复。

分层的必要性同样通用：不分层就会出现"一个巨大的 CLAUDE.md 什么都往里塞"，结果是高频变动的内容和永不变动的约束混在一起，谁也不敢删，最后没人维护。

**换项目要改什么**：只改**内容**，不改结构。铁律条数保持在个位数（超过十条就没人当铁律了）。

**最容易学错的地方**：
- ❌ 把 CLAUDE.md 写成项目介绍（"本项目是一个电商系统，使用 XX 框架……"）。项目是什么应该放 docs 让 AI 按需读；CLAUDE.md 是**每次会话都无条件加载**的，只配放"不许做什么"这种密度极高的东西。
- ❌ 把记忆写成抽象规则。原项目的记忆有个固定字段 `**Why:**`，里面写的是**事故本身**（"2026-07-10 曾因 cwd 残留……靠 rebase --onto 重写历史才修复"）。带事故的规则会被遵守，不带的会被"合理化绕过"——因为 AI 和人一样，只有知道代价才会警惕。

### 约束二：上下文有限且昂贵

**原项目的做法**：
- `PREFERENCE_INDEX.md` 开宗明义写着"**This is a router, not a second source of truth**"——只存检索信号和路径，不复制规则正文。
- `MEMORY.md` 一条记忆一行。
- `active.md` 一个战役只占一行，细节全部外链到 plan 文档。
- 只读类 skill（`/hao-task-next`、`/hao-task-list`）明确声明不加载写路径。
- 状态栏常驻显示 `ctx:NN%`。

**通用形态**：**任何会常驻上下文的文件，都必须拆成"索引层 + 内容层"，AI 先读索引，再按需读内容。**

**为什么必然通用**：上下文预算是所有模型的共同上限，而且它是**竞争性资源**——被文档吃掉的额度，就不能用来读代码和思考。更隐蔽的成本是**信噪比**：塞进去的无关内容不只是浪费，还会稀释真正重要的约束。

有一个数据很能说明问题：该项目 1790 条输入的 **prompt 长度中位数只有 60 个字符**，超过 500 字符的只占 1.2%。复杂度根本不在指令里，全在那些常驻文件里。这正是索引化的回报——指令可以短到"选 C，直接开工"，因为上下文已经就位。

**换项目要改什么**：索引的**粒度**。小项目一个 `MEMORY.md` 就够；跨十几个仓库才需要 `PREFERENCE_INDEX` 那种带 `Task signals` / `Must read when` / `Skip when` 的正式路由表。

**附带的通用推论**：**给只读操作单独做入口**。`/hao-task-next` 严格只读、绝不 commit，这不只是安全考虑——它让"我就想问问下一步该干嘛"变成一个廉价动作，不必担心 AI 顺手改了什么。任何工具集都值得把"看"和"改"分成两个命令。

### 约束三：AI 自信，而且会编——尤其编标识符

**原项目的做法**：
- 部署清单 skill 写死：**"命令必须基于项目真实代码。artisan 命令名、表名、字段名、配置键、路由 path 都要 grep 到出处，不允许凭记忆猜测。"**
- 解释类 skill 写死："**先核实，不许编**……字段名写错一个，整个解释的可信度归零。"
- 守门测试要**断言效果不是断言存在**，而且"**必须亲手验红**"（先确认测试会失败，再让它通过）。
- 知识库里有一条独立的 `incident-evidence`（事故分析证据纪律）。

**通用形态**：
1. AI 输出里凡出现**专有名词**（表名、命令名、配置键、API 路径、函数名），都要有可追溯的出处。
2. 凡是**验证性产物**（测试、检查清单、监控判据），都要先证伪一次——没见过它变红的测试，等于没有测试。

**为什么必然通用**：幻觉是模型的固有属性，不因语言或框架而变。而**最危险的幻觉恰恰是标识符**——`user_settings` vs `users_settings`、`--force` vs `--yes`，看起来完全合理，只有真跑起来才错。散文级的错误人一眼能看出来，标识符级的错误人看不出来。

这条的代价意识也通用：一份"命令全是猜的"部署核验清单，比没有清单更糟——它给了虚假的安全感，而且是在你最紧张的时刻。

**换项目要改什么**：核实手段（grep / LSP / 类型检查 / API schema），不改要求。

**一条相关的、极易被忽略的通用规则**：`aggregate-zero-is-not-absence`——**存在性判断禁用 `SUM == 0`**，只比净额会漏掉正负相抵的错误。这不是 SQL 技巧，是任何"用聚合值证明某事没发生"的场合都成立的逻辑漏洞（对账、日志统计、指标监控通吃）。

### 约束四：AI 不承担后果

**原项目的做法**：
- 【最高优先级】未经明确允许不得登录生产，**即使操作是只读的**。
- 一条真实纠正：负责人问"接下去如何排查是否一切符合预期？"，AI 直接 SSH 上生产逐项排查了。纠正是——**"『告诉我怎么查』与『替我去查』是两种授权，不能自行升级。"**
- 标准输出格式因此固定为：**目的 → 可直接复制的命令 → 每条命令看什么、什么结果算正常/异常**。
- 部署清单 skill：只读优先，有副作用的命令单独标 ⚠️ 并说明后果，默认不进清单。
- 全局铁律：只允许操作 `db_testing`；SSH 一律 non-destructive。

**通用形态**：把 **"能力"和"授权"分开写**。AI 能做某事 ≠ 被允许做某事，而且**授权不会因为"这次是只读的"而自动扩展**。默认交付形态是"方法 + 命令 + 判读标准"，而不是"我已经帮你做完了"。

**为什么必然通用**：责任不可委托这件事和技术栈无关——出事时被问责的是人。更关键的是一个行为规律：**AI 有自行升级授权的倾向**。它会把"问方法"理解成"要结果"，因为直接给结果看起来更有帮助。这个倾向在任何项目里都存在，所以边界必须写死，不能靠临场判断。

**换项目要改什么**：哪些是"生产"。个人项目里可能是"已发布的 App Store 版本"、"客户的数据库"、"主分支"。**每个项目都有一条不可逆的线，把它明确写出来。**

### 约束五：AI 天然迁就现状

这是最反直觉、也最有价值的一条。

**原项目的做法**：
- **"不要把旧代码当成必须照抄的真理。旧代码只是帮助理解业务规则、用户行为、数据结构和历史约束的参考材料。死板复制 = 迁移失败。"**
- 每个迁移开工前先画**两张清单**：
  - **冻结面**（金额口径、幂等语义、对外触达效果、共享表行形状）→ 逐字节等价，差分闸门只管这一面
  - **自由面**（模块拆分、命名、错误分型、监控、测试体系）→ 彻底放开重设计
- **"差分测试只是手段，不是目的。目的永远是更专业的架构。如果差分遇到差异，那就调整测试方式、甚至调整测试标准。"**
- 差异出现时走**三分法裁决**：① 回归 → 修新代码；② 有意改良 → 调标准并**记录裁决**；③ legacy 怪癖 → 显式决策存废。
- **"绝不为让差分变绿而在新代码里复刻 legacy 的坏结构。每次调标准都留记录——将来要能回答『绿是在什么标准下的绿』。"**

**通用形态**：**任何"基于既有东西做改造"的任务，开工前先划两张清单：必须逐字节不变的，和鼓励重新设计的。并且预先约定：差异出现时的裁决程序是什么。**

**为什么必然通用**：这是一个**力学问题**，不是某个语言的问题。AI 的最优策略天然是**最小化与现状的差异**——那样最安全、最容易通过任何检查、最不容易被指出错误。而人要的往往是"这次顺便把它做对"。两个目标方向相反。

**不显式划线，AI 一定选照抄。** 这不是它偷懒，是它在优化你给它的可见指标。你给的指标是"差分变绿"，它就会为了绿而复刻坏结构——包括在新代码里重建旧代码的耦合，只为让某个字段的字节完全一致。

**适用范围远超 legacy 迁移**：
- 换框架 / 换语言 → 冻结面 = 对外 API 契约与数据格式；自由面 = 内部结构
- 拆微服务 → 冻结面 = 跨服务消息；自由面 = 服务内一切
- 重做 UI → 冻结面 = 品牌资产、法务文案、关键转化路径；自由面 = 布局、组件、动效
- 用 AI 重写自己三年前的代码 → 同理

**换项目要改什么**：两张清单的**具体内容**。清单的存在本身、以及"差分只比冻结面"这个规则，一字不用改。

### 约束六：并发多会话会互相踩

**原项目的做法**：
- 一任务一工作树：`worktree-t127-backend`、`worktree-t131-admin-web`……命名法是 `worktree-<任务号>-<仓库>`。
- 一任务一测试库：`db_testing_t127`、`db_testing_t122`，任务收尾后 DROP。
- 所有 git 写操作**必须显式 `git -C <绝对路径>`**，绝不依赖 shell 残留的 cwd。
- **禁止裸 `git add -A`**。
- 每个改文件的流程都写着"**先读再改，保留他人改动**"。

**为什么必然通用**：只要你同时开两个 AI 会话——现在几乎是必然——共享可变状态就是竞态。而且有两个坑是 AI 特有的：

1. **cwd 是隐式全局变量**。AI 通过 shell 工作，shell 的 cwd 会在调用之间残留。原项目为此付出过两次代价：把本该提交到 docs 仓库的改动 commit 到了另一个仓库，扫走了用户 4 个未提交的 WIP 文件，靠 `rebase --onto` 重写历史才救回。**第二次事故还发现了更细的坑**：Bash 里 heredoc 之后换行再写 git 命令，heredoc 与后续行是独立语句,前面失败不会短路后面的 git。
2. **AI 倾向于用"全选"式命令**（`add -A`、`rm -rf`、`--force`），因为它们更简洁、更少出错——在单人单会话下确实如此，在并发下是灾难。

**通用形态**：
- **给每个并行任务一份可丢弃的私有工作副本**（git worktree / 独立分支 / 容器 / 独立数据库）。
- **所有写操作显式指定目标，不依赖任何隐式上下文**（cwd、当前分支、默认数据库、默认账号）。
- **写完立即核对影响范围**（`git show --stat`）。

**换项目要改什么**：隔离手段。前端项目可能是独立端口 + 独立 localStorage 命名空间；数据项目可能是独立 schema。

**一条相关的通用启发**：把上下文写进名字里。`worktree-t127-backend`、`db-vps__nightly-database-backup`——名字里带着"属于哪个任务""跑在哪台机器"。这对 AI 尤其有效，因为它经常只看得到文件名而看不到你脑子里的归属关系。

### 约束七：AI 的默认语言不是你的语言

**原项目的做法**（记忆里有整整一组）：
- 术语首次出现必须一句话解释；讲问题按"**是什么 → 为什么改 → 不改会怎样**"三段展开，**宁可篇幅长，也不要行话式浓缩**。
- 提编号必须同时说明它指什么："看到『要么先做 T-24，要么回到 T-1 的 SB-8』这种只有编号的话**完全不知道在说什么**。编号是给文件系统用的，对话是给人看的。"
- **中文自造词比英文术语更危险**——"台账""口径""闸门""收编""兜底"看着像中文，读者不会意识到是术语，"只会一直不懂又不好意思问"。
- 让人做选择时的判据："**不是『我说得对不对』，而是『用户看完能不能不反问就直接选』。**"
- 测试汇报禁用"全量回归"，必须写清类型、目录、数量，**以及没跑什么**。
- 金额解释首句必须标明是理论数还是实际到账。

**哪些通用、哪些是个人化的**：

| 内容 | 通用性 | 说明 |
|---|---|---|
| "读者看完能不能不反问就直接决定" 这个判据 | **完全通用** | 它是可操作的验收标准，不依赖读者是谁 |
| 编号必带含义 | **完全通用** | 任何用 ID 的系统（Jira、Linear、issue 号）都成立 |
| 禁自造简称，直接说文件名 | **完全通用** | AI 特别爱造概括性简称，因为它压缩得好看 |
| 汇报要说"没做什么" | **完全通用** | 见下，这条单独值得强调 |
| 术语解释的**深度** | 需按人调整 | 该负责人是产品设计出身，所以要展开；对资深后端同事就是噪音 |
| 具体的用词禁令（"营业额""资金面"） | 不通用 | 是这个人 + 这个领域的特定坑 |

**为什么"说清没做什么"这条极其通用**：AI 的默认汇报是**只报做了什么**——不是它想隐瞒，而是"没做的事"不在它的注意力里。而风险恰恰藏在那儿。"跑了 312 个单元测试和 45 个集成测试，**没有浏览器 e2e，本仓库不存在此类测试**"和"测试全绿"，是两条信息量完全不同的消息。**要求 AI 报告缺口，是把它的盲区变成你的已知项。**

### 约束八（附加）：AI 会用提问转移决策责任

单列出来，因为它足够重要且足够反直觉。

**原项目的做法**：记忆 `autonomous-execution-no-check-ins` —— 接了活就自主连续做，不要每完成一个小增量就停下问"要我继续吗"。这类确认式提问被明确斥为"**愚蠢的问题**"。只在**真正需要拍板的产品/技术决策**才停，且**问题要具体、带推荐答案**。汇报用"已做完 X，继续做 Y"，不用"要不要我做 Y"。

**为什么通用**：确认式提问的成本是 **往返延迟 × 次数**，而且它把决策责任悄悄推回给你——每次"要我继续吗"都在要求你重新加载一遍上下文。真正需要你的判断的问题，一次会话里通常不超过三五个。

**通用形态**：不是"永远别问"，而是**预先定义停下来的条件**。可以直接抄的一组条件：
- 涉及产品取舍（用户会看到不同的东西）
- 涉及不可逆动作（部署、删数据、发消息）
- 两个方案代价相当且你有偏好
- 发现的事实与任务前提矛盾

除此之外一路做下去。

**配套要求也通用**：问的时候**带推荐答案**。"A 还是 B？"是把问题原样退回；"建议 A，因为 X；选 B 的话代价是 Y"才是把工作做完了再交给你。

## 三、第二类可迁移物：不是原则，是"形状"

有些东西的价值不在道理，在**结构本身可以直接照抄**。

### 3.1 任务板的形状

```
active.md    唯一的优先级视图，Now / Next / Later 三区
             Now ≤ 3 行（强制聚焦）
             区内行序 = 优先级，调优先级 = 移动行
             一个战役只占一行，细节全部外链
icebox.md    新想法默认落这里，不允许直接插进 Now
completed.md 只追加，带完成日期和结果一句话
```

状态机：`Backlog → Planned → In Progress → Deployed → Done / Dropped`

**为什么通用**：它同时解决两个需求——AI 每次开工需要**一个确定的入口**（"开工前先读 active.md 的 Now 区"），人需要**一眼看到下一步**。两个需求都与业务无关。

原项目的 README 里还论证了一件反直觉的事：**为什么不按状态拆文件**（backlog/doing/done 各一个）——因为"优先级排序是**跨状态**的全局判断，拆开就失去了一眼看清下一步做什么的能力"。这个论证同样通用。

**最该带走的单点：`Deployed ≠ Done`。** AI 天然把"代码写完 / 合并了"当作终点。加一个显式的中间态（已上线、观察期中），强制"验证优先于新工作"，是任何项目都受益的一条。观察期几天可以改，这个状态的存在不该改。

### 3.2 交付文档的形状：plan / spec / pending-confirmations 三件套

| 文档 | 管什么 |
|---|---|
| `*-plan.md` | **why**，拍板依据、runbook、回滚预案 |
| `*-spec.md` | **how**，工程契约。**🔴 冲突时以本文为准** |
| `*-pending-confirmations.md` | 开发收官后的待确认清单 |

每份开头固定写：版本与变更来源、读者是谁、**分工与冲突时以谁为准**、涉及哪些仓库、**⛔ 明确不动哪些**、范围排除。

**为什么通用**：AI 最容易犯的两个错——**越界改了不该改的**，和**两份文档打架时自己挑一份信**——正好被"⛔ 排除清单"和"冲突时以谁为准"这两行直接封掉。这两行的写作成本是十秒，收益是消除整类事故。

还有个细节值得抄：spec 里有一节 `§0.0 十分钟看懂本方案（通俗导读；工程契约从 §1 开始）`——**把给人看的导读和给机器执行的契约物理分开**，两边都不用妥协。

### 3.3 汇报的形状：A / B / C / D 四段

```
A. 我自行拍板的取舍     —— 每条写「做了什么 / 为什么 / 状态」，不认可就说
B. 必须由你亲手执行的事 —— 生产操作、需要你的权限的事
C. 验收的几道门各自走到哪了
D. 测试跑了什么、结果如何、【没跑什么】
```

**为什么通用**：这是 **AI 向人交付一段工作的最小完备结构**。A 让你只审需要审的（而不是重读全部 diff），B 划清责任边界，C 给状态，D 给缺口。任何一段 AI 完成的工作都能用它汇报，与内容无关。

原项目的用法还多一层：负责人逐条回复后，AI **在同一份文档里回填处置状态**（"A1–A8 全部按建议通过；B3 经核实确属未导，保留为部署步骤"）。这样这份文档同时是**交付物和决策记录**，不需要额外维护一份会议纪要。

### 3.4 写 skill（给 AI 的可复用指令）的工艺

从十几个自建 skill 里提炼出的五条，与 skill 的内容无关，是纯工艺：

1. **规范与执行分离**——skill 只写"怎么做"，规范正文放在知识库里，skill 去读它。原项目的原话："该文件是本 skill 的**唯一规范真相源**——skill 本身不复制规范内容，以防两处维护脱节。"
   > 这是软件工程里的 DRY，但在 AI 场景下后果更严重：两份规范漂移后，AI 不会报错，它会**挑一份执行**，而你不知道它挑了哪份。
2. **只读的明确声明只读**——"绝不改文件、绝不 commit、绝不执行任务"写在 skill 正文里。
3. **默认落在最保守的位置**——新任务默认进 Icebox，不替用户排期。
4. **不确定就问，不猜**——"多个候选 → 列出候选问用户，不猜"在多个 skill 里逐字重复。
5. **解析要宽容**——"中英文混用、空格多少、全角/半角冒号、vs/VS/对比 都要能认"。人不会按格式敲命令。

还有一条元规则：**自建的一律加 `hao-` 前缀，无例外**。理由是第三方 skill 也会用 `task-*` 这类通用名，会混淆。任何人装了几十个第三方 skill 之后都会遇到这个问题。

### 3.5 工具的分层：通用引擎 vs 每项目配置

差分测试工具的分法：
- **通用引擎**（`SKILL.md` + `runner.py`）放 skill 目录，所有项目共享
- **每项目配置**（启动配方、页面清单、测试账号、已知差异登记表）放 `<项目>/tools/`，随项目版本化

外加一条**防漂移铁规则**：配置**永远读你敲命令时所在的工作树里那份**，与被对比的两个版本无关；而且 runner 每次开头必须打印它实际用的文件绝对路径和行数/hash。

**为什么通用**：任何"要在多个项目里重复用的工具"都会遇到"引擎和配置混在一起"的问题。而**打印实际用的配置路径**这个习惯，专治一类极难排查的 bug——工具跑了、绿了，但用的是另一份配置。

## 四、有代价的做法：别无脑抄

诚实地说，这套体系里有几处是**用风险和维护成本换速度**的，新项目或新手直接照抄会出事。

| 做法 | 代价 | 什么时候才划算 |
|---|---|---|
| `skipDangerousModePermissionPrompt` + 常用 bypass 权限模式 | 失去了逐次确认这道网 | **只有在前置约束足够硬时**：铁律已写死、生产不可达、默认只读、多仓库有 worktree 隔离。这些没到位之前，逐次确认是你唯一的网 |
| 装 200+ 个 skill | **实测：207 个里 180 天内真正用过的只有 69 个（33%）**，清理掉 48 个。skill 会随项目演进而失效，维护它不漂移是真实成本 | 收藏 ≠ 能力。建议从"你每天做两遍以上的事"里挑第一个来固化。审计方法见第七节 |
| 85 条 memory | 会过期。记忆本身也承认"反映的是写入时的事实，引用文件前先核实还在不在" | 值得，但要接受它需要偶尔清理 |
| `active.md` 已长到 136 KB | 常驻文件变大会反噬上下文预算 | 需要定期归档（原项目已经把 Icebox 拆成独立文件来减体积，理由写在 README 里） |
| capture → triage → canonical 三段知识流水线 | triage 是高判断成本操作，需要真的定期做 | 跨多个项目、需要沉淀共性时才值得。单项目直接写 memory 就够 |

**给实习生的话**：这套东西是**四个月、上百次会话、几次真实事故**长出来的，不是设计出来的。别一次性搭完，会烂在那儿。

## 六、深挖：一个"个人工程知识库"的可迁移设计

前面第一节把 `practices` 归为持久层的第三层就带过了。它值得单独拆开——因为这一层是**最难自己想出来、但设计一旦看到就能直接抄**的部分。

### 6.1 它解决的是 memory 解决不了的那部分

| | memory | 知识库 |
|---|---|---|
| 作用域 | 单项目 | 跨项目 |
| 触发写入 | 被纠正的当场 | 定期 triage |
| 形态 | 碎片、事故驱动 | 抽象过、有适用边界 |
| 寿命 | 项目结束即失效 | 越用越值钱 |
| 成本 | 极低 | 高（需要真的做 triage） |

分界线不是"重要不重要"，是**"这条经验换个项目还成立吗"**。成立 → 值得抽象进知识库；不成立 → 留在 memory 就好。

### 6.2 最该抄走的一张表：四种知识载体的职责划分

README 里有这张表，我认为是整个知识库设计里最有价值的一段：

| 载体 | 权威内容 |
|---|---|
| **项目仓库** | 当前实现、准确命令、项目专属架构和 runbook |
| **知识库** | 跨项目可复用的**原因、规则、边界和验证方法** |
| **Skill** | Agent 可以执行的**工作流、判断逻辑和停止条件** |
| **Slash prompt** | Skill 的入口与参数转发 |

配套一条铁律：

> **同一内容不得在多个载体中维护全文副本。** 项目和 skill 应链接到知识库的 canonical practice；知识库通过 provenance 指回产生证据的项目版本。

**为什么这条极其通用**：这是"和 AI 协作时的信息架构"的最小完备划分。绝大多数人的做法是把这四种东西全塞进一个 `CLAUDE.md`——结果是那个文件既是项目介绍、又是编码规范、又是操作手册，最后大到没人敢删任何一行，而 AI 每次会话都要把它整个读一遍。

四种载体的区分依据其实是**"谁在什么时候需要它"**：项目实现是写代码时按需读的，跨项目规则是决策时路由到的，skill 是被显式调用时加载的，slash 只是个入口。混在一起 = 全部变成常驻成本。

### 6.3 最锋利的一行 frontmatter：`basis: preference | evidence | mixed`

README 的原话：

> **个人偏好不伪装成普适事实；经验性最佳实践也不伪装成个人审美。**

实测 18 篇 canonical 文档的分布：

| basis | 篇数 | `last-verified` | 例子 |
|---|---|---|---|
| `preference` | 7 | 一律 `null` | 编程原则、命名规则、生产 SSH 边界、任务管理 |
| `evidence` | 8 | 有具体日期 | 等价性测试、查询优化、分层健康检查、事故证据纪律 |
| `mixed` | 3 | 有日期 | BFF 选型、前端渲染架构选型、macOS 开发指南 |

**为什么这是整个库里最值得单独抄走的设计**：因为 AI 对这两类知识的正确处理方式**完全相反**。

- `preference` 类：**你说了算，不需要证据**。AI 不该质疑，也不该"帮你优化成业界最佳实践"。`last-verified: null` 不是缺失，是**声明这条不靠验证成立**。
- `evidence` 类：有验证状态和日期。AI 在新场景下**应该重新验证**，过期了应该主动说"这条最后验证是 7 月，你现在的栈变了"。

不做这个区分的后果有两个方向，都很糟：
1. AI 把你的个人审美当成科学到处套用（"规范里说不用某种视觉风格" → 在一个完全不同的项目里也拦着你）；
2. AI 把验证过的血泪教训当成"个人口味"，遇到阻力就随手推翻（"这只是偏好，我换个做法"）。

**一行 frontmatter，把"我喜欢"和"我验证过"分开。** 这是我在整份材料里见到的最高杠杆的一个小设计。

### 6.4 生命周期与状态机

```
[ inbox ] --补背景、证据、边界--> [ field-note ] --真实项目验证+抽象--> [ canonical ] --过时--> [ archive ]
```

状态：`draft`（判断合理但证据不足）→ `verified`（至少一个真实项目验证过）→ `adopted`（已成为多项目默认）→ `deprecated`（不再推荐，**正文必须指向替代实践**）

**为什么通用**：知识和代码一样会过期，区别是**没有编译器会告诉你**。`status` + `last-verified` 是唯一的替代品——它让"这条还算数吗"变成一个可以被机器读到的字段，而不是靠人记。

配套的命名规则同样通用：

> 不创建 `-v2`、`-final`、`-new` 一类并行版本。新文档用 `supersedes` 指向它替代的旧文档；旧文档标 `deprecated` + `replaced-by`，再移入 `archive/`。

**为什么这条对 AI 场景尤其重要**：和前面 skill 那条同源——**AI 遇到两份同主题文档不会报错，它会挑一份执行，而你不知道它挑了哪份。** 人看到 `plan-v2.md` 和 `plan-final.md` 会去问一句，AI 不会。

### 6.5 晋升门槛：canonical 文档的九个必答项

一篇经验性实践进库前必须写清：

```
Context      解决什么问题
Rule         推荐做法（要能执行和验证）
Why          机制和证据，不只是偏好
When to use / When not to use    适用与不适用边界
Trade-offs   收益 / 代价 / 已知限制
Failure modes  常见失败方式 + 如何识别（表格形式）
Verification 可重复执行的检查
Provenance   来自哪个项目、哪个 commit、哪份证据、什么时候验证的
```

**为什么这九项通用**：其中 **When not to use、Trade-offs、Failure modes、Verification** 这四项，正好是 AI 生成"最佳实践"时**永远会漏掉**的四项——它天然产出的是"应该这样做"，不是"什么时候不该这样做、代价是什么、怎么知道它失效了"。

**把这四项设成必填，等于强制把"结论"变成"可判断的知识"。** 一条没有边界和代价的最佳实践，在下一个场景里就是误导。

实测这个门槛是真落实的——provenance 表里是真的 commit SHA：

```
| Project          | Commit                                     | Evidence                                    | Verified at |
| internal-project-docs | 7f713a463bf24eb1d062c20ae68f80917ad1438e   | playbooks/legacy-equivalence-testing.md     | 2026-07-11  |
```

**还有一个容易被忽略的细节**：模板明确写着 preference 类**可以跳过验证证据**——"个人偏好可以由本人的明确表达直接成立，不要求伪造项目验证"。

门槛**分类型**而不是一刀切，这很关键。否则个人偏好永远达不到 evidence 类的门槛，就永远进不了库，只能散落在聊天记录里。

### 6.6 检索契约里更硬的两条

第二节讲过"索引化"。这里补两条更反直觉的：

**（1）明确授权 AI 不读。** 索引里写着"没有匹配项时无需遍历整个知识库"。

一个 20 篇以上的知识库，"全读"已不可行。而"选读"必须有**明确授权**——否则 AI 只有两种行为：全读（爆上下文）或随机读（不可预测）。**给它一个"可以不读"的许可，它才会稳定地按索引读。**

**（2）明确划出"非生效区"。** 索引里写着：`inbox/`、`field-notes/`、`archive/`、`templates/` 一律不算生效偏好，除非用户明确要求查看。

这条解决的是一个必然出现的问题：知识库里**大部分文件是半成品**。没有这条，AI 会把一条你随手记下、还没验证的 inbox 笔记，当成你的既定规范来执行。

**（3）冲突处理写死成程序**，不靠临场判断：

```
当前用户明确指令 > 当前项目事实与项目级 AGENTS.md > 命中的 canonical 偏好 > 框架默认
冲突时：暴露冲突，保留项目约束，等人决定。不许静默覆盖任何一方。
```

"**不许静默覆盖任何一方**"是重点。AI 的默认行为是挑一个更"权威"的执行下去，你根本不会知道发生过冲突。

### 6.7 Provenance 纪律：三条精准得像是踩过坑的规则

AGENTS.md 里这三条，我认为每一条都对应一次真实的教训：

1. **"从项目提炼内容前必须先检查 diff，避免把本地未提交状态误写成已验证事实。"**
2. **"当前工作树存在未提交修改时，必须区分『已提交证据』和『本地观察』。"**
3. **"从多个来源归纳时，分别列出来源，不用一个来源替另一个来源背书。"**

**为什么通用**：AI 在"总结经验"这件事上有一个稳定的失败模式——**把刚才在本地看到的临时状态，写成"已验证的普遍事实"**。它刚跑通一个本地实验，就会写下"这个方案是可行的"，而那个实验用的是你没提交的临时改动。

第 3 条针对的是另一个稳定失败模式：**用一个来源给另一个来源背书**。AI 归纳多份材料时会自然地合并成一个自信的结论，掩盖掉"其实只有一处证据、另外两处只是提到过"这个事实。

### 6.8 这个库自己规避掉的四个反模式

README 明确列了"本仓库不存放"，每一条都正对 AI 的一个默认倾向：

| 禁止项 | 对应的 AI 默认倾向 |
|---|---|
| 不为结构完整预建空目录（"分类由已有内容驱动"） | AI 极擅长生成**看起来完整**的目录树，然后你有 12 个空文件夹 |
| 不批量搬运 session / plan / 聊天记录 | AI 觉得"都存下来"最安全，结果知识库变成垃圾场 |
| 不存"只有结论、没有背景和证据的最佳实践" | AI 生成的正是这种——听起来正确、无法验证 |
| 不放完整 skill 副本 | 复制比链接容易，但会立刻产生第二份真相源 |

### 6.9 成本的诚实评估

- 18 篇 canonical + 10 篇未 triage 的 inbox + 9 篇已归档
- **inbox 里最早的一条是 2026-07-25，积压了一个多月**

这说明 triage 是**真实的、会被拖延的成本**。但积压本身不致命——capture 廉价正是设计目的（"Capture 的价值是忠实和快速，而不是聪明地整理"）。堆在 inbox 里的笔记至少没丢。

**给新项目的建议**：不要一上来就建知识库。**只有当同一条经验在第二个项目里又需要时**，才把它从 memory 升级进知识库。第一次遇到写 memory，第二次遇到才抽象——这个门槛能挡掉大部分伪通用经验。

## 七、如何审计自己的 skill 使用率（本次实测方法）

第四节说"207 个 skill 只用过 69 个"。这个数字是怎么算出来的，方法本身可复用。

### 7.1 证据要取三层，缺一层就会误删

| 层 | 数据源 | 覆盖 | 抓得到什么 | 抓不到什么 |
|---|---|---|---|---|
| 1 | `~/.claude/history.jsonl` | 长（10 个月） | **你手敲的 slash 命令** | 模型自动触发的 |
| 2 | `~/.claude/projects/*/*.jsonl` 里的 `"skill":"x"` | 短（本机只留 34 天） | **模型自动触发 + 工具调用** | 更早的历史 |
| 3 | skill 之间的**互相引用** | — | 被别的 skill 调用的"零件型" skill | — |

只用第 1 层会误删所有**靠 description 自动触发**的 skill——实测里 `hao-explain-only`（11 次）、`hao-deploy-verification-checklist`（11 次）、`hao-explain-to-doc`（10 次）的手敲次数都是 **0**，全靠模型自动识别触发。**只看 slash 记录，这三个会被当成"从没用过"删掉。**

### 7.2 引用检测必须收紧，而且必须做传递闭包

两个坑，我这次都踩了：

**坑一：用 skill 名做子串匹配会假阳性泛滥。** `setup`、`review`、`spec`、`implement`、`learn`、`teach` 这些是英文常用词,在任何正文里都会出现。第一轮跑出 91 个"被引用"，收紧成只认显式调用语法（`/name`、`skills/name`、`` `name` ``、`[[name]]`、`"name"`）后降到 83，可删数从 47 升到 55。

**坑二：只查一层引用会断链。** 依赖是有链条的：`gstack`（在用）→ `ios-qa`（没直接用过但被 gstack 调用）→ 它自己又调用别的。必须从"用过的 skill"出发做**传递闭包**，把所有可达的都保留。做了闭包后保留数从 152 升到 158，可删数从 55 降到 49。

### 7.3 软链是第三个坑（这次真踩了）

`~/.claude/skills/` 里有 22 个是**符号链接**，指向共享仓库：

```
code-review        -> ../../.agents/skills/code-review
vercel-react-best-practices -> vercel-claude-skills/skills/react-best-practices
```

我按"未使用"删掉了 `vercel-claude-skills` 这个**容器目录**——但 `vercel-react-best-practices` 是**在用的**，它是指向该容器内部的软链，于是变成断链。已从备份恢复。

**通用教训：清理前先列出所有软链及其指向，把"被在用软链指向的目标"一并纳入保留集。** 删完必须跑一次断链自检：

```bash
for f in *; do [ -L "$f" ] && [ ! -e "$f" ] && echo "断链: $f -> $(readlink $f)"; done
```

### 7.4 删除前必须做的两件事

1. **全量 tar 备份**（本次 497 MB，`~/.claude/backups/skills-backup-<时间戳>.tar.gz`）。恢复单个是一条命令：`tar -xzf <备份> skills/<名字>`。
2. **把自己写的和第三方装的分开报告**。本次删掉的 48 个里有 4 个是自己写的 skill（`hao-task-list`、`hao-organize`、`hao-dev-preferences-setup`、`hao-tech-seo-loop`）——它们和"顺手装了没用过的第三方 skill"性质不同，值得单独确认一次。

### 7.5 真正该删的理由：不是磁盘，是"描述污染"

这是本节最重要的一句：

> **每个 skill 的 `description` 都会进入模型选择 skill 时的候选判断。无用的 skill 越多，误触发和漏触发就越多。**

一个装了 200 个 skill 的环境里，模型每次都要在 200 条描述里判断"这次该不该用哪个"。描述之间语义重叠（`polish` / `distill` / `normalize` / `optimize` / `quieter` / `bolder` 六个都在讲"改进现有东西"）会直接降低命中率——**你自己写的那个精准 skill，会被一堆语义相近的第三方 skill 稀释掉。**

所以"留着不用，反正不占地方"是错的。**它占的是每次会话的判断预算。** 这条结论与栈无关，任何 skill / plugin / tool 机制都成立。

## 八、一句话总结

如果只带走一句话：

> **把与 AI 的协作，当成给一个能力极强、但每天失忆、且不承担后果的同事做"入职手册 + 权限管理"。**

本文所有内容都能从这句话推出来：
- **每天失忆** → 外部持久层（约束一）、索引化（约束二）、任务板与文档形状（第三节）、知识库的载体划分与生命周期（第六节）
- **能力极强但会编** → 证据纪律（约束三）、冻结面/自由面（约束五）、汇报要说缺口（约束七）、`basis: preference vs evidence`（6.3）、provenance 纪律（6.7）
- **不承担后果** → 授权边界（约束四）、隔离与显式定位（约束六）、停下来的条件（约束八）

而"入职手册"这个比喻还能再推一步：**手册也需要版本管理和定期体检**。第六节的状态机（`draft → verified → adopted → deprecated`）和第七节的 skill 使用率审计，就是这份手册的体检流程——**你给 AI 的规则和工具，本身也会过期，也需要被清理。**
